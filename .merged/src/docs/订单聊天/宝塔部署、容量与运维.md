## 1. 最小组合和托管选择

同一台服务器、同一业务域名，Go聊天服务与PHP订单独立进程；不新增服务器、聊天后台或Kafka/Redis Streams。Go自身不需要PHP运行时；复用图片优化的受限CLI依赖现有PHP，图片本机解码/可选OCR helper需独立锁定C++或Python/ONNX运行依赖；这不把Go消息核心改回PHP。

| 部件 | 职责与保护 |
| --- | --- |
| Nginx 443 | 订单/后台给原PHP；`/chat/ws`及`/chat/api/v1/`给Go |
| Go `chatd serve` | 1进程，HTTP/WSS、聊天应用和有界DB池；只监听127.0.0.1:9501，内部口9502 |
| Go `chatd worker` | 1进程，媒体/业务事件恢复及清理；CPU并发起点1，ASR网络并发起点2，不抢满主机 |
| PHP FPM/既有任务 | 订单、登录/后台凭证交换、权限栅栏、通知适配、钱包及独立通话共享资源CallQuota（通话不接钱包）；不逐消息代理Go |
| MySQL/Redis/七牛 | MySQL持久真源（按保留期清理），Redis辅助，七牛私有媒体直传/直取，不经Go/FPM搬运大文件 |

**主路径用Supervisor托管两个Go前台进程**，配置可复用到测试/生产；没有现成Supervisor时也可用宝塔“网站→Go项目”/应用管理器或systemd，择一即可。不同面板版本入口/插件有差异，先核实实际可用项，不要求安装停更插件。不能让宝塔项目管理器和Supervisor/systemd同时守护同一端口，更不能用nohup、go run或分钟cron代替常驻管理。[宝塔官方Go教程](https://www.bt.cn/bbs/thread-93034-1-1.html)、[Supervisor配置](https://supervisord.org/configuration.html)。

## 2. 部署前核对与目录

1. 备份订单数据库、站点Nginx配置、PHP版本/扩展和既有计划任务；记录CPU/RAM/磁盘/端口/连接数基线，确认9501/9502未占用。
2. Go代码仍在workers仓库，拟`chat/`；二进制在可信构建环境生成，锁定受支持工具链、go.mod/go.sum与来源SHA。部署同服务器Linux/amd64或arm64产物，匹配架构；纯Go依赖可用`CGO_ENABLED=0`，引入CGO时另核对系统动态库，不能保证所有二进制都静态。
3. 产物附SHA-256、源码SHA、Go版本、GOOS/GOARCH、协议版本及兼容的PHP/数据库版本。服务器仅运行预编译二进制，不必安装Go编译器；保留CA证书和时钟同步。构建侧按[Go工具链文档](https://go.dev/doc/toolchain)固定版本，不在部署时无意下载latest。
4. 目录建议`/www/server/bixuan-chat/releases/<release-id>/chatd`，`current`指向生效版本；配置`/www/server/bixuan-chat/shared/chat.json`，临时目录`shared/tmp`，日志`/www/wwwlogs/bixuan-chat/`。所有目录均在网站公开根目录外。
5. 运行账号用专用`bxchat`非root；管理员负责发布目录和current切换，账号只读二进制/配置，只有tmp/日志可写。配置root:bxchat、0640，目录按需0750、二进制0750；不要chown整棵订单站点或chmod777。若复用PHP CLI图片优化，以受限任务接口授予必需资源，勿给Go写订单配置权限。

已实现的S01 CLI：`chatd version`、`chatd check-config --config <path>`、`chatd serve --config <path>`、`chatd worker --config <path>`。当前check-config校验JSON/环境/回环地址/池预算，不联网；加--probe才读取配置环境变量并只读探测MySQL/Redis，仍不打印密钥或自行建表。S01无迁移，不运行PHP升级器；后续有正式迁移才按升级体系执行，不能直接把本文当安装脚本。

## 4. 宝塔Nginx站点配置

在**现有PHP网站**设置→配置文件中加入下列server级location，保留原证书、PHP include、伪静态与所有订单路由；不为Go重复创建绑定相同域名/443的站点。宝塔反向代理界面若不能表达精确路径和拒绝规则，使用站点配置文件。新增Go项目时关闭自动绑定此业务域名，避免生成配置覆盖原PHP站点。

```nginx
location = /chat/ws {
    proxy_pass http://127.0.0.1:9501;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $remote_addr;
    proxy_read_timeout 120s;
    proxy_send_timeout 120s;
    proxy_buffering off;
}
location ^~ /chat/api/v1/ {
    proxy_pass http://127.0.0.1:9501;
    proxy_http_version 1.1;
    proxy_set_header Connection "";
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $remote_addr;
    client_max_body_size 64k;
    proxy_connect_timeout 3s;
    proxy_read_timeout 30s;
    proxy_send_timeout 30s;
    proxy_buffering off;
    proxy_cache off;
}
location ^~ /chat/ { return 404; }
location ^~ /internal/ { return 404; }
```

proxy_pass不加末尾斜杠，保留完整/chat路径。64k是元数据HTTP上限，文本单请求仍按协议≤16KB；大文件直传七牛。示例假设Nginx直接接公网；有CDN/WAF时先限定可信real_ip来源，再设置真实IP，不信客户端随意传入的转发头。Go只信本机代理，校验Origin/Host及允许的客户端场景；浏览器后台使用限权Bearer、严格同域CORS，cookie管理动作仍需CSRF保护，不能用Origin替代认证。

Nginx配置保存后先运行宝塔实际Nginx二进制的`nginx -t`，通过再平滑reload；核对宝塔自动重写配置后自定义location仍在。[官方WebSocket反代文档](https://nginx.org/en/docs/http/websocket.html)要求正确传Upgrade/Connection，超时配合应用心跳，不是把timeout无限拉长。不要对/chat套静态缓存、强制下载、WAF验证码或HTML错误页；HTTP错误保留可识别的状态码和安全JSON。

Go内部9502不出现在proxy_pass中，安全组/防火墙不开放9501/9502/Redis/MySQL；PHP内部桥接也必须本机独立监听或显式拒绝公网并有服务签名，不能把普通PHP路由仅改名internal。

## 6. 小程序、后台与上线顺序

1. 微信后台为实际生产/测试域名分别核对request、socket合法域名，七牛uploadFile/downloadFile域名与HTTPS证书；真机不依赖开发工具“不校验合法域名”。仍同域分路径，不增加ws子域名。
2. 按正式迁移规则先补PHP ChatBridge、授权栅栏/会话撤销与事件通道，开关默认关闭；核对存量订单授权的有界初始化和版本，未知栅栏不开放。
3. 上传校验后的Go版本目录，check-config通过，以非root账号启serve/worker，检查本机`/livez`（进程）与`/readyz`（DB/关键授权依赖）；详情不对公网暴露。Redis/媒体等降级依赖单列状态，不能因七牛异常宣称文字完全不可用。
4. 加Nginx配置、语法检查/reload；以真实短效凭证测试HTTP401/403/正常请求、WSS101+auth.ok与完整seq/change_cursor补收，101本身不算认证或消息成功。
5. 先隔离测试站，再白名单正式订单真机灰度；验关单/改派/禁聊/登出撤权、9图部分失败、后台分页和通知幂等，再开文字/图片。语音消息、视频消息、双通道免费通话各独立门禁，通话不启收费，不默认随Go进程启动启用。
6. 核验PHP部署SHA、Go二进制version、协议/配置版本、DB迁移与来源SHA相符；Git main更新只表示源码同步，既有PHP webhook不能自动视为已构建或重启Go。后续扩展部署脚本必须明确构建、校验、切换、重启和健康检查步骤。

## 7. 发布、停机与回退

发布采用新release目录→校验→切换current（同文件系统原子换链接）→受控重启→健康检查→真机/探针；不要原地覆盖正运行的二进制。失败切回兼容的上一版本并重启；加法迁移保留，不能删已保存聊天/订单数据或回滚已执行SQL校验。PHP/Go协议先兼容后启用，避免新Go依赖未部署的桥接字段。

Go收到TERM：readyz转不可接新任务→停止新请求/领取任务→有限等待已入事务命令→明确关闭/排空WebSocket→退出。应用主动维护WS连接注册表；[Go HTTP Shutdown](https://pkg.go.dev/net/http#Server.Shutdown)不会自动等待/关闭被接管的WebSocket。应用排空目标≤30秒，小于Supervisor45秒；worker以持久租约恢复未完成任务，不把收到信号当已发布。前台客户端退避重连，unknown发送按原ID查结果。

单Go进程重启会同时影响聊天HTTP/WSS，短时不可用是首期边界。WSS单通道故障且HTTP健康才有HTTP降级；整进程/主机故障不能靠PHP或另一域名兜底写消息。需要无中断更新时再建设双Go实例、多实例路由/临时状态和一致性验证，不承诺切链接即零停机。

## 8. 容量、监控与故障

先做30/100/300前台连接混合订单API、文本突发、read_seq、回前台双游标、9图、审核与通知压测；目标观察原订单p95退化约≤10%、峰值资源余量约30%，均不是已验证容量承诺。Go serve/worker数据库池合计预算单独核定，不按Socket数开DB连接；goroutine、外部HTTP/子进程、发送队列/帧大小有界，慢端断开后sync。MySQL5.7不使用仅8.0支持的SQL。

| 指标/异常 | 处置 |
| --- | --- |
| Go退出/重启、goroutine/RSS增长、慢端队列 | 监控重启次数/延迟/队列，进程守护恢复；持续异常关闭新发送，订单继续 |
| PHP FPM过载/停机 | 原订单受影响；已有合法Go凭证/授权与检测依赖可用时文字可继续，新登录/续凭证/钱包暂停 |
| Redis不可用/PubSub丢失 | 已存消息不丢；新ticket暂停、HTTP有效凭证可用，限流保守；seq/change_cursor核对恢复 |
| MySQL失败或授权不可确认 | 不ACK、不使用旧缓存放行；订单与聊天共享数据库风险仍存在 |
| 媒体/凭证代理/检测/七牛失败、临时盘高水位 | 暂停或重试相应媒体/审核，不记违规；检测必需依赖失效不能先放行文本 |
| PHP通知消费者积压、桥接事件失败 | 持久租约/幂等重放，监控固定首次到期、到期复查/未读簇时延及渠道受限；仅按真实已读/权限取消对应聊天范围，online/偏好不抑制order，正式业务事件独立 |
| 会话/权限变更与分页 | 监控双游标/过期resync；列表摘要快照建议10分钟，历史/引用有界，不全量载入 |

心跳约30秒、pong等待10秒、服务端90秒回收、Nginx120秒，重连1/2/4/8/16/30秒加抖动；全局账号摘要在持续前台30～60秒核对一次，另有当前会话双高水位；仅当前聊天页5～10秒退避HTTP降级，恢复立即停止，退后台停止所有前台轮询。presence/typing在单Go实例内存，不每次心跳写Redis/DB。普通限流可从突发5条/10秒、持续60条/分钟起测；语音/合集按逻辑发送及媒体成本分别限额。

## 9. 留存、恢复与拆机

MySQL备份会话/成员区间/消息与变更/已读偏好/禁聊申诉/事件消费和聊天审计；PHP继续备份订单/钱包/计费账本。七牛正式对象与元数据一致恢复；失败临时源/转换件有TTL/磁盘配额，合集逐对象核对引用及legal_hold。普通媒体签名建议≤60秒；撤回停止新签/清普通缓存，已存副本不能远程收回。

S22交付留存配置矩阵：普通正文/正式媒体、临时上传与已确认待审意图、拒绝/撤回/举报证据、审计、变更日志/游标、导出文件及备份各自的TTL、清理批次、legal_hold和删除责任。高风险证据30天只是建议起点，不把所有类别都默认无限保留；具体必要期限在发布前确定并告知。删除要同步摘要、引用安全占位、缓存和检索，签名过期不等于对象已删。

仅恢复旧数据库备份无法获知备份后发生的撤回/撤权/删除。需独立可恢复的最小安全变更记录与连续恢复水位（如校验过的增量日志/删除与撤权记录），保留范围覆盖可恢复备份窗口，不能与旧快照一起回退。恢复先关闭用户读取/发布/通知消费者，按记录重放安全状态与清理、重验PHP权威授权、对齐水位后才开放；安全增量缺失时保持受影响历史不可见并登记恢复缺口，不能宣称已安全重放。记录与备份同样受权限/保留约束，不复制全部聊天正文。

## 10. 本机图片helper与人工模式


两监听GET/HEAD /livez仅表示进程存活。只有内部监听提供/readyz：scope=infrastructure_only、business_enabled=false；MySQL通过检查返回200，Redis不可用仍200但redis.state=unavailable；MySQL不可用/禁用返回503。健康响应是依赖快照，字段有required/state/安全code/checked_at，不是普通业务错误信封。结果定时刷新缓存，HTTP查询不重复访问依赖；停机后不再恢复ready。对外readyz、聊天API/WSS、metrics及pprof仍404。

实际服务集成测试默认跳过，需要专门提供隔离MySQL/Redis：设置CHAT_INTEGRATION=1、CHAT_INTEGRATION_MYSQL_ADDR、CHAT_INTEGRATION_REDIS_ADDR及可创建临时库/账号的CHAT_INTEGRATION_ADMIN_PASSWORD，再运行go test -race -count=1 -v ./...。只允许显式本机端点，随机bixuan_test_s02_*库与bxchat_test_*账号，结束清理；绝不能配置真实业务数据库/管理员凭证。加CHAT_INTEGRATION_CHATD_BIN=<绝对二进制路径>可一起验证实际HTTP进程的健康/降级/关闭路由/TERM。本轮实际验证MySQL5.7.42、Redis7.0.11；线上5.7.44/PHP/真机/宝塔另验。

### 19.2 同环境恢复控制目录

建议独立受保护卷 /www/backup-control/bixuan-chat/<env>，**不放在旧数据库备份、网站根目录或 release/current 中，也不能随旧主机镜像回退**。PHP维护账号可写，Go账号只读；目录0750、文件0640，禁止组/其他用户写。离机备份最新控制锚点及密钥，权限和访问审计独立管理。

### 19.3 备份、增量与恢复演练顺序

1. 保持发布开关关闭，明确恢复范围与最后可信来源。先 block，停止两个Go进程和相关PHP写者/提醒消费者，等待在途事务结束；gate不是撤销已经返回到用户设备的数据。
2. 在来源完整且静止时 capture，检查前后真实 binlog 坐标一致；保护最新签名 checkpoint.json 与 latest.json。基线数据库快照应与其安全检查点对应，另保留覆盖该基线到最后可信高水位的独立连续 binlog 归档。不可只备份旧库内的一个水位。
3. 恢复旧备份后先 verify，预期发现备份后撤回、权限或回执缺失并保持 blocked。缺失原登录、后台权限、trigger、授权/成员代次或对象清理记录时，不跳过对应表继续上线。
4. 对独立归档运行 python3 chat/scripts/seal-binlogs.py --control <控制目录> --backup-checkpoint <基线签名检查点> --archive <只读归档目录> --mysqlbinlog <明确可执行路径>。工具拒绝缺文件、倒序、错来源/环境、截断尾部或校验和失败；不执行其中SQL，也不输出行内容。必须确认 latest 代表最后可信高水位；归档源本身落后/遗失时，保持隔离并登记缺口。
5. 由维护账号在隔离目标按准确库名与起止位置重放已核验 binlog，保护原SQL/日志，不打印用户数据。重放包括幂等回执、provider_unknown/已发送状态和账本，不启动业务消费者。多库/跨服务恢复需使用各自一致的完整备份制度，不能只重放聊天表却宣称整个订单/钱包已经恢复。
6. 再 verify，全安全指纹一致后，release 还核对独立连续增量证明，才将 gate 写 ready。同环境重启两个Go进程，确认授权trigger、check-config --probe、版本、WSS和受保护动作；最后恢复消费者和灰度。
7. 故障回退先停新任务，切回经验证且与当前数据库加法结构兼容的旧二进制/配置；保留原数据、幂等ID和权限代次，不回滚已发布历史SQL。缺失增量/对象即继续隔离，不用“恢复成功”掩盖数据缺口。

**独立安全锚点和可信归档是前提**。同时恢复成旧版本的数据库、控制文件和密钥，或无法获知灾难前最后提交水位时，软件不能推断之后发生过的撤回/撤权；这类恢复不满足安全开放条件。
