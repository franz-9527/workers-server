# 宝塔计划任务说明

> 长期维护文档，不再按版本复制文件。

订单、退款、验收、评价、服务费、维修提醒以及测量自动确认/冻结释放统一由同一个 CLI 调度入口执行。不要为每个业务动作重复创建计划任务。

## 推荐配置

1. 宝塔面板 → 计划任务。
2. 任务类型选择“Shell 脚本”。
3. 任务名称：`壁选师傅订单自动任务`。
4. 建议每 1 分钟执行一次。
5. 示例命令：

```sh
/www/server/php/83/bin/php /www/wwwroot/worker/bin/scheduler.php all
```

站点目录不是 `/www/wwwroot/worker` 时只替换项目绝对路径；PHP 命令以服务器实际 PHP 8.3.36 安装路径为准。不要再把标准输出使用 `>> storage/logs/scheduler.log` 重定向到应用日志；应用自身已经维护 `scheduler.log`，重复重定向会绕开应用日志的用途边界并制造额外体积。宝塔自己的任务执行日志只作为 CLI 执行记录使用。

## 当前统一任务范围

`task=all` / CLI `all` 由服务端统一调度当前已注册任务，包括但不限于：

- 订单超时与自动取消；
- 已批准订单退款的可靠原路提交与失败重试；
- 平台最终争议裁定后退款的自动原路提交；
- 双方已同意退款、完成 Web 财务核账后的自动原路提交；
- 72 小时自动验收；
- 自动评价与维修提醒；
- 平台服务费相关定时处理；
- 消息可靠队列重试；
- 无引用媒体清理；
- 用户钱包充值纠错退款兜底与台账对账；
- 测量成果自动确认；
- 测量冻结到期释放。

> **退款执行不要再新增第二条宝塔任务。** `ApprovedOrderRefundRetryBridge` 已挂在现有 `scheduler.php all` 上。管理员完成最终争议裁定，或双方退款协议完成 Web 财务核账后，后续微信原路退款由下一轮统一任务提交；网络失败会继续使用同一退款单号幂等重试。普通 `pending_review / created` 退款不会因此被自动批准，只有明确的已批准取消退款、最终争议退款和 `bilateral_refund_execution_prepared` 退款进入该桥。

> **不要为 `wallet_reconcile` 再新增第二条宝塔计划任务。** 继续只保留现有每分钟一次的 `scheduler.php all`。充值纠错退款提交/查单仍会每分钟检查；钱包余额与不可变台账的全量 SUM 对账由服务端内部节流为每小时一次。管理员如需立即检查，可直接在后台“系统 → 计划任务”点击对应任务的“立即执行”，无需输入 Shell 命令。

具体任务清单以当前代码中的 scheduler 注册表为准，不在本文复制固定版本清单。

## 首次验证

在宝塔中手动执行一次，确认：

- 命令正常退出并返回成功结果；
- `storage/logs/scheduler.log` 可产生近期运行摘要；
- 后台计划任务/审计没有连续失败；
- 真实支付、退款、冻结等资金动作仍以服务端状态机和支付回调为准。

不要使用网页 URL 定时访问替代 CLI 命令，以免受到登录态、反向代理超时、缓存或访问控制影响。

## 运行记录与失败排查

- 后台“未解决的业务失败”列表提供“立即重试”。该操作只提前当前失败的重试时间，并通过同一个 `SchedulerService` 重新执行；业务条件、媒体引用检查、维护状态和 MySQL 互斥锁仍然有效。
- 单独点击某个任务的“立即执行”属于管理员明确诊断操作：`media_cleanup` 可立即重试尚在退避期的孤儿媒体，`wallet_reconcile` 可立即做一次完整台账对账；点击“执行全部”则不强制绕过这些节流。
- `scheduler_runs` 只是近期调度诊断，不是订单或资金业务流水；“扫描到候选但没有真正处理”的成功运行只保留最新一条。后台手动执行和宝塔自动执行使用同一数据库互斥锁，撞车时其中一次会安全跳过。
- `wallet_reconcile` 的“钱包一致”属于巡检通过，不再把每个钱包计入 `success_count`。
- 每类失败运行在 `scheduler_runs` 最多保留最近 20 条；具体业务失败仍保存在 `scheduled_job_failures`。
- `media_cleanup` 会遵守 `scheduled_job_failures.next_retry_at`，失败后按退避时间重试；后台“未解决失败”查看具体错误。新代码同时把本次具体媒体错误写入 `scheduler_runs.error_message`，不再只显示“请查看 scheduled_job_failures”。
- 已经成功删除、重新产生引用或不再属于清理候选的媒体，其旧未解决失败会自动标记为已解决。

## 文件日志容量规则

`storage/logs` 是短期运行诊断，不是长期业务台账。日志维护由应用自动执行：

- `scheduler.log`、`scheduler-error.log` 等高频计划任务通道，活跃文件达到约 4 MB 后滚动；归档总量约 8 MB，且每个通道最多 3 份归档；
- 其他活跃日志达到约 8 MB 后滚动；归档总量约 16 MB，且每个通道最多 3 份归档；
- 归档超过 30 天自动删除；活跃日志如果连续 30 天没有再写入，也会自动清空旧内容，因此已经修复且一个月未复现的 `app.log` 异常不会永久留在后台；
- 日志维护最多每 10 分钟执行一次，使用文件锁避免并发清理影响业务；
- 后台“系统 → 运行日志”仍可按 7/15/30/60/90/180 天手动清理或清空单个日志；
- 订单、资金、退款、消息状态等真实业务事实必须查数据库业务表和审计表，不能依赖文件日志长期留存。

## 维护规则

后续新增定时业务时：

- 继续接入统一 scheduler；
- 更新本文件中的业务范围说明即可；
- 不要让高频成功心跳承担业务审计职责，业务诊断优先使用 `scheduler_runs` 和 `scheduled_job_failures`；
- **不要再新增“宝塔计划任务说明-Vx.x.x.md”之类版本化文档。**
