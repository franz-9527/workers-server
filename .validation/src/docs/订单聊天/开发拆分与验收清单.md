# 开发拆分与验收清单

[主设计](订单聊天系统设计与开发说明.md)实施附录，2026-10-21 Go/PHP 定版。**已进入工程开发；代码、自动化、现场联调与部署状态分别记录，最新状态只维护在第19节。未完成现场验收的能力保持生产开关关闭，不将隔离测试视为真实渠道或上线通过。**

架构基线：

> 单服务器 + Conversation Core + 首期 OrderConversationPolicy + 单 Go 聊天实例 + MySQL 消息真源 + `seq` 增量补收 + `read_seq` + 七牛媒体直传 + 现有 Redis 辅助 + 现有通知 `message_outbox`。

首期不要求 Inbox / delivery ACK / delivery_token / 聊天专用 Outbox / dispatcher。

## 1. 分阶段开发计划与每轮边界（2026-10-21，执行唯一入口）

聊天开发原有 **8个大阶段、23个工作单元S01～S23**；2026-10-26追加 **S24商家订单协作群**，不重排已经完成的历史编号。语音/视频/通话仍列EXT01～EXT06，未来私信另列F1～F3。S是执行顺序、EXT是后续能力，验收表的P0/P1是功能优先级，P01/M01等是既有验收用例编号，三者不能混用。原P0～P8粗分期由本节替代，已有C/G/U等验收编号保留。

**用户已指定聊天独立使用`chat`分支，未经后续明确指示不得合并或提交到其他分支。** 默认一次“继续开发/下一阶段”完成一个最早未完成的S工作单元；本次用户已明确要求连续开发，故每个单元验证并只提交chat后直接进入下一单元，不等待再次确认。当前进度见第19节。

### 1.1 对话容量、额度和接续规则

- 每轮以约15～25分钟为工作目标，先选择一个能实现、验证和提交的功能闭环；时间是拆分参考，不是完成时限或总工期承诺。不为了凑时长开启额外功能。
- 开始前只读本节和第19节进度、主设计相关章节、对应验收及实际代码；按需≤200行读取，不在每轮重读所有聊天文档/全仓库，不把完整日志和重复diff塞入对话。上下文/工具输出接近容量时，先完成当前可验证单元并记录交接。
- 预计单元过大，在开发前拆成Sxx.a/Sxx.b等子单元，保留父编号，不重排后续编号；每个子单元必须有明确产物/验证/开关边界。原子性、权限、幂等不可为了分轮而省略，先后端再前端时双方契约要先固定。
- 同一轮只扩当前单元及必要依赖；发现既有问题区分“阻断本轮”与“后续修复”。阻断项先修，不在未通过时越过依赖推进；可延期项写入第19节，不另建零散待办文档。
- 中间检查用定向测试；每个S单元结束执行影响域所需完整回归，跨语言/SQL/资金单元包含集成或并发验证。按[CI规范](../持续集成与测试执行规范.md)复用现有门禁，不在每轮无关重跑全仓重型测试，也不为节省额度跳过必需门禁。依赖/runner不可用明确记“未执行/待验证”，不能记完成或作为正式集成通过。
- 聊天开发只提交用户已授权的`chat`分支；本轮从最新main建立，后续默认沿chat接续。不得自动同步main、dev/2.6.0或测试仓库，不发起合并，等待用户明确指示。此项是本聊天任务对通用dev→main规则的明确例外，不改变其他业务分支规则。未完成业务保持关闭，框架完成不等于聊天已上线。
- 不承诺工具或会话能精确读取剩余额度。长测试保留可追踪的命令/run与状态，不把启动测试当通过；一轮在第19节记录可恢复位置，下轮核实状态后继续，不能留下未说明的后台任务。

实施拆分（2026-10-26）：S24.a再分为 **S24.a1 权威快照与成员代次契约** 和 **S24.a2 原表真源/同事务桥接/nullable绑定与投影**。a1交付独立PHP策略、Go严格读取契约及跨语言专项，不接API、不使现有Reader接受schema 3、不调整SQL或生产开关；a2完成后才能把a标记完成。a2必须覆盖已创建群在指派空档/关单/售后中的持续状态，不能仅靠当前有师傅的快照构造器代替完整业务桥接。

补充规则：

- 施工地址中的业主手机号只在PHP可信侧与当前登录账号的当前已验证手机号比较；Go和邀请接口不返回完整手机号。
- 邀请管理权限来自真实商家组织/订单权限、订单真实用户/手机号匹配业主、当前正式施工师傅身份或平台管理员；不来自群内自选身份标签。
- 当前正式施工师傅可以邀请自己的帮手或团队成员加入；受邀帮手选择“团队师傅”，不因此成为订单正式指派师傅，也不获得报价/结算/取号等师傅业务权限。
- 分享不设置可加入人数，不做1/2/3选择器、来源方配额或公平领先算法。是否能继续加入只检查：邀请有效、邀请人仍有资格、群未关闭、当前人数未达到管理员设置上限。
- 每个受邀成员记录实际`inviter_actor_id`和邀请代次；邀请人可踢出自己邀请的普通协作者，但不能踢系统成员、平台人员或别人邀请的人。更高权限商家管理者/平台管理员按业务权限处理。
- 分享邀请支持重新生成；重新生成后旧海报中的小程序码和旧微信分享代次立即失效。分享海报保留品牌、项目标题、邀请说明、小程序码和有效期，不显示人数额度、精确地址或手机号。
- 管理员前端新增“协作群人数上限”，默认10，建议3～50可调。降低到低于当前人数时不自动踢人，只禁止继续加入；提高后立即按新上限生效。
- 群达到人数上限只是暂时阻止加入，不必销毁仍在有效期的分享；有成员退出/被移除后，只要邀请仍有效即可继续加入。
- 普通受邀成员默认只从加入版本读取；自动商家/当前师傅/手机号匹配业主的历史范围由其各自系统成员起始版本决定，禁止客户端申请任意补看历史。

### 8.3 后台/离线

推荐形成聚合“未读提醒意图”：

```text
第一条未读
→ 首次10秒固定聚合到期（首期上限30秒），连续新消息不后移
→ 发送前检查真实read_seq + 权限 + 本轮预算/渠道条件
→ 到期仍未读就评估订阅，online/当前页不能代替已读
→ 持续未读按配置复查补提醒，达到预算保留超时未读摘要
→ 高价值业务事件才评估短信兜底
```

验收：

| 编号 | 场景 | 预期 |
| --- | --- | --- |
| N05 | 10 秒内用户重新打开并读完 | 外部提醒取消 |
| N06 | 20 条连续文字 | 不产生 20 条订阅任务 |
| N07 | 同会话已提醒仍未读 | 冷却只合并重复，到期按轮次重检；有界补提醒后保留超时未读，不能永久取消 |
| N08 | 微信订阅额度可用 | 只发送聚合提醒 |
| N09 | 微信订阅不可用、普通私信 | 默认不短信轰炸 |
| N10 | 报价/支付/退款/争议等高价值事件 | 按现有高可靠短信策略处理 |
| N11 | 微信/短信均失败 | 消息本体仍可回到小程序后 sync |
| N12 | 连续发消息/重启恢复 | 首次到期不滑动，20条不变20次通知；提醒轮次与预算不重置 |
| N13 | 旧轮次已读与新消息并发 | target_seq/cluster_version条件回写，不能取消新到消息的提醒意图 |
| N14 | 订阅无授权/额度耗尽或达补提醒预算 | 保留未读/角标及渠道受限/超时摘要，不伪记成功、不默认增加付费短信 |
| N15 | 聊天冷却期间发生正式业务事件 | 预约/加价/退款/验收/售后按原事件规则触达，不受聊天偏好或轮次上限抑制 |
| N16 | 订单转只读/账号仅禁发 | 合法历史未读仍可提醒，不因can_send=false取消；撤权则按当前can_read范围过滤 |

### 8.4 与现有 outbox 的边界

必须通过代码审查确认：

```text
chat message persistence != message_outbox delivery
```

允许：

```text
聚合后的 conversation_unread / trade_action_required
→ 现有 message_outbox
→ 微信订阅 / 短信
```

禁止：

```text
每条 message × recipient
→ outbox
→ 等设备 ACK
```

## 13. 单服务器压测与扩容验收

至少混合：

- 30 / 100 / 300 前台 WSS；
- 普通订单列表/详情；
- 文本突发；
- read_seq；
- presence/typing；
- 回前台 sync；
- 少量媒体处理；
- 外部通知 outbox；
- 未来发现页上线后再加瀑布流分页/点赞/评论。

观察：

- CPU/load；
- RAM/Swap/OOM；
- Go 聊天服务 RSS/调度/消息处理延迟；
- PHP-FPM 队列/p95；
- MySQL p95/慢查询/连接；
- Redis latency/memory；
- sync QPS/平均补收量；
- 媒体 worker CPU/队列；
- outbox 积压与第三方延迟。

建议观察目标：

- 原订单 API p95 退化尽量 ≤ 约 10%；
- 峰值仍保留约 30% CPU/RAM 余量。

它们只是扩容判断指标，不是硬性容量承诺。

扩容顺序：

1. 媒体先拆；
2. 瀑布流 SQL/CDN/缓存先优化；
3. 单 Go实例 真成瓶颈再同机多网关；
4. 整机持续高负载再拆第二服务器；
5. 最后才考虑更重投递设施。

## 14. 代码审查红线

以下任一出现，应在开发阶段阻止合并：

- 网关直接写订单 SQL；
- conversation 表强制 `order_id NOT NULL` 且无抽象层；
- WSS 与 HTTPS 各写一套发送逻辑；
- 把 Redis 当聊天历史真源；
- 心跳/typing 每次写数据库；
- 图片/视频 Base64 走 WSS；
- 每条聊天生成一条微信订阅/短信；
- 普通私信订阅失败后无条件短信；
- 管理员查看私信无审计；
- 聊天文字直接改成交价/订单状态；
- 为未来私信提前引入 Kafka/IM 集群而没有真实瓶颈。
